The core difference: I'd invert the relationship between narrative and structure. The current design makes agent-authored markdown the source of truth (`filing-log.md` frontmatter feeds Phase 3; `_summary.qmd` YAML feeds `build_tra_database.py`) and derives the database from it at the end. From scratch, I'd make a structured, append-only ledger the spine from day one and generate the narratives as views over it. Most of the other differences follow from that.

**1. Events and claims as the primary data model, not Phase 4 output.** The domain is inherently event-sourced — origination, amendment, assumption, termination — yet events only materialize as a table in Phase 4d. I'd have the Phase 2 reading agent emit schema-validated event records (JSON, validated at write time, quarantined on failure) *alongside* its narrative entry, with a source-filing citation on every row. Phases 3 and 4 then become queries and renderings over the ledger rather than re-parsing prose and frontmatter. Parsing YAML out of agent-written markdown is the most fragile joint in the current design — there's no schema enforcement at the moment of writing, which is exactly when the agent has the context to fix a malformed record.

**2. Contract identity as a first-class claims graph.** Cross-CIK consolidation is the hardest problem in the pipeline, and the current design defers it to a phase that re-reads everyone's logs. I'd instead give every exhibit an ID at acquisition time and let Phase 2 write explicit link assertions ("exhibit A = exhibit B, evidence: …, confidence: …") into a links table as it encounters them — the agent often *knows* the cross-firm link while reading the merger 8-K. Phase 3 shrinks to resolving the link graph into contract clusters and flagging ambiguous components for review. This also makes corrections cheap: revising one link doesn't invalidate any narrative.

**3. Key everything by CIK, not slug.** The slug-lock-on-first-encounter logic, collision suffixes, and the merger CSV exist because directories are named by human-readable slug. Slugs are display names; CIKs are identity. From scratch, the firm tree is `data/filings/<cik>/<accession>/` and slugs live only in a display table. Half of `registry.py`'s complexity disappears.

**4. One incrementality mechanism instead of a refresh phase.** Phase 5 is a bolted-on re-run path. If every stage is a function from content-addressed inputs to outputs with recorded input hashes — which the manifest already gestures at — then "refresh" is just "run the pipeline; already-done work no-ops." The `.phase1-done` marker is a symptom of not having this: it exists because downstream can't otherwise tell whether the manifest is complete. A small DAG driver (even just pixi tasks calling a make-style dispatcher) would replace both the marker and Phase 5.

**5. An evaluation harness for the agentic stages.** The design treats agent judgment (substance-over-form classification) as a prompt-spec problem and punts QA to a future document. From scratch, I'd hand-label a gold set of ~20–30 firms *before* building the Phase 2 skill, record model and prompt version on every extraction, and regression-test prompt changes against the gold set. Without this, you can't tell whether a skill "refactor" made classifications better or worse — and this project will refactor its skills repeatedly.

What I'd keep, because it's genuinely right: the five-phase decomposition; the deterministic-code-for-Phase-1 / agent-for-Phase-2 split; chronological per-firm reading with the log as durable agent memory (the narrative earns its keep for the judgment calls — it just shouldn't double as the database); the rate-limited cached client layer; atomic writes and the `fetch_status` vocabulary; monthly FTS sweep with window halving (forced by the 10k cap; the alternative — bulk index files plus local full-text — is more reproducible but much heavier, and I'd make the same call).

If you wanted to retrofit rather than rebuild, the cheap wins are #1 and #2 — since Phase 2 isn't built yet, having its skill emit validated event and link records alongside the narrative costs almost nothing now and prevents the markdown-parsing debt entirely. #5 is worth doing before the Phase 2 skill too. #3 is a judgment call (the tree already exists but is regenerable from the manifest), and #4 I'd fold into whatever orchestration you add when Phases 2–4 start chaining together.
