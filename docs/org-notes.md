# If we were designing the pipeline from scratch

The biggest change is where the official record lives. As planned now, the reading phase writes a narrative log for each firm (its `filing-log.md`), and the database gets assembled at the end by pulling facts back out of those write-ups. I would flip that: facts go into the database the moment they are found, and the readable summaries are generated from the database. Most of the changes below follow from this one.

1. Record events as they are found, not at the end. Everything in this project is an event: a contract is signed, amended, taken over by an acquirer, terminated. In the current plan, a table of these events only appears in phase 4, built by parsing the summary files written earlier. Instead, the moment the reader identifies an event in a filing, it should add a row to an events table — alongside its narrative entry — and the row should be checked right then, while the reader still has the filing open and can fix a problem; rows that fail the check go into a review pile. The checking is cheap because `docs/tra-background.md` already lists the allowed statuses and transaction types and the rules for dates and citations; the table just enforces them. Recovering the same facts later from finished summaries is the weakest link in the current design, because nothing checks a summary's accuracy or format at the time it is written.

2. Treat "is this the same contract?" as a running question, not a late phase. The same TRA routinely appears several times — a draft in the IPO registration statement, the executed copy in an 8-K, re-attached copies in later annual reports — and across companies when a contract changes hands in a merger. The background gives the reader a five-part test, so the judgment gets made constantly during reading; the current plan just buries the outcome in the narrative for phase 3 to re-read. Better: give every downloaded contract document an ID number and record each verdict as a data entry the moment it is reached, with the evidence and a confidence level. This also respects the reader's limited working memory. An agent reading the buyer's merger filing has never read the seller's filings and cannot hold every other firm in its head, but it can look up the seller's CIK in the database and either link to the existing contract or record "matches a contract at CIK X, not yet read" for a later pass. The current plan instead sends the whole question to phase 3, where one agent must weigh every firm's log against every other — the step most likely to outgrow an agent's working memory as the firm count reaches the hundreds.

3. Refer to firms by CIK in every saved record, never by name. Records currently refer to a firm by its folder nickname, so the nickname must never change once assigned — that is what the collision suffixes, `data/cik-mergers.csv`, and about half of `registry.py` protect. If manifest rows, event rows, and contract links all use the CIK instead, the nickname carries no weight: folders keep their readable names for browsing, a stale or corrected name breaks nothing, and most of the naming machinery disappears.

4. Make every phase resumable instead of adding a refresh phase. Phase 5's entire job is keeping the database current as new filings appear. If each phase keeps a record of what it has already processed, refreshing is just running the pipeline again: finished work gets skipped, new filings flow through. The download phase already works this way internally — `manifest.parquet` lists every document fetched so far — and it also writes an empty flag file, `.phase1-done`, to signal that downloading finished. That flag points at the gap: it exists because phase 2 otherwise has no way to tell whether the download record in front of it is complete. If every phase were resumable, neither the flag nor phase 5 would be needed.

5. Build the answer key before building the automated reader. Phases 2 and 3 rest on an AI assistant's judgment — recognizing, say, that an "Exchange and Termination Agreement" is really a TRA termination. The current plan defers quality control to a future document. I would do it first: classify twenty or thirty firms by hand, note which version of its instructions the assistant was running for each entry, and score every revision of the reader against the hand-classified firms. The set should include the near misses the background catalogs — agreements that resemble TRAs but are not, disclosures that resemble terminations but are not — since those are the failures we would otherwise not notice until late.

What I would keep, because it is right: the first four phases themselves (discover, read, consolidate, publish — item 4 folds the fifth into them); ordinary code for the mechanical download work, with the AI reader reserved for judgment calls; reading each firm's filings in date order while keeping a running log, since the log doubles as the reader's memory on firms with long histories — the narrative earns its keep for judgment, it just should not double as the database; the polite treatment of the SEC's servers, meaning the request rate limit and the local cache; searching month by month, which the SEC's search tool forces on us by capping any one query at 10,000 results (downloading the SEC's bulk filing indexes and searching them ourselves would be more reproducible but far more work, and I would make the same call again); and `docs/tra-background.md` itself, which already holds the classification rules the design above leans on.

What is worth adopting now rather than in a rebuild: items 1 and 2 cost almost nothing, because the reading phase has not been built yet — design it from the start to write event rows, and verdicts on which documents are the same contract, in a fixed format, and the problem never arises. Item 5 also belongs before the reader exists. Item 3 is now only a rule about what new records point at, not a reorganization of existing folders, so it costs nothing to follow from here on. Item 4 can wait until phases 2 through 4 start running as a chain.
